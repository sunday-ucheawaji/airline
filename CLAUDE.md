# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Spring Boot multi-module microservices GDS (Global Distribution System) for an airline platform: flight search, seat selection, booking, payment, and notifications, behind an API gateway with JWT auth, Eureka service discovery, a Git-backed Config Server, and Kafka for async events. See `README.md` for the full original feature/architecture writeup (services table, data-flow diagrams, security model, API examples, circuit-breaker thresholds) — it's accurate for the platform as a whole, with one correction: the actual Java package root is `com.sunday` (e.g. `com.sunday.common_lib`, `com.sunday.services`).

**`user-service` is currently mid-redesign** against `airline-gds-complete-user-airline-design.md` (an airline-only GDS identity/auth design doc). It has diverged from the rest of the repo in ways described below — read that section before touching `services/user-service`.

**`airline-core-service` is also mid-redesign**, one phase behind `user-service` (onboarding pipeline + `AirlineMembership` built; document storage and invitations not yet started, per-airline role/permission checks not yet started) — read that section before touching `services/airline-core-service`.

**`api-gateway` was rewritten (2026-09-21)** and is now the repo's single, enforced RBAC entry point — read the `api-gateway` section before touching it or before adding any new route/endpoint.

## Commands

Build everything:
```bash
mvn clean package -DskipTests          # from repo root
```

Build/compile just what you're touching (much faster than a full reactor build):
```bash
mvn -pl common-lib,services/user-service -am compile -q
```
`-am` ("also make") pulls in upstream reactor dependencies (here, `common-lib`). This works fine for `compile`/`install`/`test` goals.

Run a single service locally — **do not** use `-pl <module> -am spring-boot:run` from the repo root. Maven runs the `spring-boot:run` goal against every project in the resulting reactor, including the root and `services` aggregator POMs (packaging `pom`, no main class), and fails immediately with `Unable to find a suitable main class`. Instead:
```bash
mvn -pl common-lib install -DskipTests   # once, so it's resolvable from the local repo
cd services/user-service                # or whichever service
SPRING_PROFILES_ACTIVE=local mvn spring-boot:run
```
(On Windows PowerShell: `$env:SPRING_PROFILES_ACTIVE = 'local'` first, or set it in an `application-local.yaml`-adjacent way — the `local` profile is what supplies concrete `localhost` values for the datasource and Config Server URL; the base `application.yaml` uses unresolved `${...}` env-var placeholders that assume a container/cluster environment.)

Local infra a service needs before it'll boot cleanly: MySQL (`localhost:3306`, one DB per service, e.g. `airline_user`), Config Server (`localhost:8888`), Eureka (`localhost:8761`). `spring.config.import` is `optional:configserver:...`, so a service will still start without the Config Server, just without whatever config it serves (locations, Flyway/JPA settings for `user-service` — see below).

Run tests:
```bash
mvn -pl services/user-service test
```
Apart from `api-gateway` (which has real security tests), every service currently only has a boilerplate `*ApplicationTests.contextLoads()` smoke test — no real test coverage exists yet anywhere else in the repo.

Full stack via Docker Compose: `docker compose -f docker-compose/docker-compose.yml up -d` (see README's "Running the Project" section for env vars required — Gmail SMTP, Twilio, Razorpay/Stripe, `JWT_SECRET_KEY`).

## Architecture (condensed — see README.md for the full picture)

- **Module layout**: `common-lib` (shared DTOs/enums/exceptions/events, package `com.sunday.common_lib`) → `cloud/` (api-gateway, config-server, service-registry) → `services/*` (11 business services, each its own Spring Boot app + its own MySQL DB, package `com.sunday.services`).
- **Auth model**: JWT is validated once at `api-gateway` (which also enforces platform-role RBAC — see its section); the gateway forwards `X-User-Id` / `X-User-Email` / `X-User-Roles` headers downstream, always overwriting any client-supplied copy. Business services **trust these headers** rather than re-validating the JWT themselves — this is a repo-wide convention, and it is only safe because the gateway's port (5000) is the only one docker-compose publishes.
- **Inter-service calls**: OpenFeign clients, each with a `*ClientFallback.java` and a Resilience4j circuit breaker (per-client thresholds in README).
- **Async events**: Kafka, e.g. `booking.confirmed` / `payment.completed`, consumed by `seat-service` and `notification-service` in parallel (saga-by-choreography, no distributed transactions).
- **IDs are `Long`** everywhere (not UUID) — an explicit, repo-wide decision; don't introduce UUID PKs in one service without updating the gateway and every Feign consumer of that service.

## `user-service` redesign — read before editing this service

`services/user-service` is being rebuilt incrementally against `airline-gds-complete-user-airline-design.md`, and has already diverged from both that doc and the rest of the repo in ways worth knowing up front:

- **`User.role` was removed entirely.** The old global `UserRole` enum (`ROLE_SYSTEM_ADMIN` / `ROLE_AIRLINE_OWNER` / `ROLE_CUSTOMER`, still defined in `common-lib`) is no longer stored on `User` at all — replaced by the `Role`/`UserPlatformRole` model below. `CustomUserDetailsService` now grants real authorities (`ROLE_<role.getName()>`) from a user's `PLATFORM`-scoped `UserPlatformRole` grants, and both `login()` and `refresh()` pick them up. Enforcement lives at `api-gateway` (roles only, `ROLE_GDS_ADMIN` — see its section); `user-service` itself is still `permitAll` and does no role/permission checks, and `Permission` rows aren't consumed by anything yet.
- **`AirlineMembership`-granted (`AIRLINE`-scoped) roles were deliberately left out of JWT authorities** — a synchronous Feign call and an async Kafka-mirror (`airline-core-service` → `user-service`) were both designed; the mirror was actually built and then reverted. Reason: a flat `GrantedAuthority` string can't carry *which* airline a role applies to, so it could only ever produce a coarse "holds role X on some airline" signal, never real per-airline authorization — that correctly stays a local, live DB check in `airline-core-service` (`AirlineServiceImpl.requireActiveMembership`), independent of the JWT. Don't re-attempt mirroring airline roles into the JWT without reading this reasoning first.
- **A separate `Role`/`Permission`/`RolePermission` model exists** (own tables, own CRUD under `/api/roles`, `/api/permissions`) — deliberately **not** wired to the old platform `UserRole` enum or to the User entity. `Role` now has a `scope` (`PLATFORM` or `AIRLINE`, default `AIRLINE`, migration `V8`): `AIRLINE`-scoped roles (`OWNER`/`ADMIN`/`VIEWER` — `OPERATIONS_MANAGER`/`BOOKING_AGENT` deliberately not created yet, since flight-ops/booking don't exist in this phase) are granted via `AirlineMembership` in `airline-core-service` (built), which stores the `roleId` as a logical reference — but only `OWNER` is ever assigned so far (at onboarding approval, via the `airline.owner-role-id` config value; invitations aren't built), and nothing yet checks the role's permissions — membership *existence* is all that's enforced. `PLATFORM`-scoped roles (`GDS_ADMIN`, for reviewing onboarding applications) have their own direct grant mechanism instead, since there's no membership to hang them off: `UserPlatformRole` (migration `V9`), assigned via `POST/DELETE /api/roles/{roleId}/users/{userId}` and read via `GET /api/users/{userId}/roles`. Assigning an `AIRLINE`-scoped role through that endpoint is rejected (`403`) — it's `PLATFORM`-only. No Flyway seed data for any of this (consistent with the rest of `roles`/`permissions`) — a real 4-role/10-permission set (`GDS_ADMIN`, `OWNER`, `ADMIN`, `VIEWER`) has been created and wired through the API in the live dev DB as part of verifying this, though — not throwaway test junk, don't delete it without checking.
- **`User` fields changed**: `fullName` → `firstName`/`lastName`/`middleName`; `phone` → `phoneNumber`; `verified` → `emailVerified`. `common-lib`'s `UserDTO` was updated to match, which is a **breaking change** for `booking-service`'s and `payment-service`'s `UserClient` Feign clients (they still expect the old shape/path) — updating those was explicitly deferred, not forgotten.
- **Flyway was added to `user-service` only** (`services/user-service/src/main/resources/db/migration/`) — other services still rely on implicit Hibernate schema generation. **Spring Boot 4 gotcha**: `flyway-core`/`flyway-mysql` on the classpath is *not* enough to trigger migrations — `FlywayAutoConfiguration` was split into its own artifact, `org.springframework.boot:spring-boot-flyway`, which must be an explicit dependency too (see `services/user-service/pom.xml`). Without it, Flyway silently never runs (no `flyway_schema_history` table, no error) while Hibernate's `ddl-auto: validate` then fails with a confusing "missing table" error — this cost real debugging time once already.
- **`spring.jpa.hibernate.ddl-auto` and `spring.flyway.*` for `user-service` live in the Config Server's repo**, not in the local `application.yaml`/`application-local.yaml` — check there (or query `http://localhost:8888/user-service/local` while the Config Server is up) before assuming schema behavior from the local YAML alone.
- **Auth response shape**: `AuthResponse.user` is `AuthUserDTO` (no `password`/`username` fields at all, structurally), not the shared `UserDTO` — `UserController` no longer references `UserDTO` at all; it's kept only because `booking-service`'s and `payment-service`'s `UserClient` Feign clients still declare it as their return type (the currently-stale-shaped downstream consumers).
- **JWT access tokens are short-lived (15 min)**; refresh tokens are opaque random strings (SHA-256-hashed at rest, never stored raw), support rotation, and detect reuse by revoking every active token for a user if an already-rotated token is presented again — that revocation is deliberately `noRollbackFor = UserException.class` on `refresh()`, because the rejection thrown right after it would otherwise roll the revocation back and silently disable the only stolen-refresh-token defense. **The JWT secret and issuer have no fallback anywhere** (`JWT_SECRET_KEY`, `JWT_ISSUER`) — `user-service` and `api-gateway` must be given the *same* values or the gateway rejects every token. The algorithm is pinned to HS256 on both sides. Logout revokes the refresh token only; there is no access-token blacklist, so an access token (and any role it carries) stays valid until its 15-min expiry.
- **Email verification and account lockout are now enforced** (not decorative): `signup` no longer issues any tokens — just a "check your email" response; `login`/`refresh` reject an unverified account (`EMAIL_NOT_VERIFIED`), a locked account (`ACCOUNT_LOCKED`, after `auth.max-failed-login-attempts` consecutive bad passwords, for `auth.account-lockout-minutes`), or a non-`ACTIVE` `User.status`. Failed-login tracking and the account-locked/not-active checks happen before password verification, so (by design, like most systems) a locked account reveals its lock state to an unauthenticated caller — that's an accepted tradeoff, not an oversight.
- **`DataInitializationComponent`'s seeded admin account only runs under the `local` Spring profile** (`@Profile("local")`) and reads its password from `bootstrap.admin.password` (only defined in `application-local.yaml`) — it must never run, and never gets a config value to run with, outside local dev. It also seeds the `PLATFORM` `GDS_ADMIN` role onto that admin, since the gateway restricts role assignment to `GDS_ADMIN`; there is no production bootstrap for the first admin yet.
- **`user-service` has no authorization of its own** — access to `/api/users` (list/lookup), `/api/roles` and `/api/permissions` is restricted at `api-gateway`. Don't add local checks without reading the gateway section first.
- **Multi-write service methods are `@Transactional`** (`AuthServiceImpl.signup/login/verifyEmail/resendVerification/refresh`, `RoleServiceImpl.assignPermissionsToRole`, `TokenCleanupScheduler.purgeExpiredTokens`) — keep that pattern for any new method that writes more than one row/table in one logical operation; Spring Data's `save()` is otherwise transactional per-call, not per-business-operation. Watch for the `refresh()`-style exception: if a throw *after* a write is meant to reject the request while still keeping that write, you need `noRollbackFor`, not a bare `@Transactional`.
- **A daily scheduled job (`TokenCleanupScheduler`, 3am by default, `auth.token-cleanup-cron`) purges expired rows from `refresh_tokens` and `email_verification_tokens`** — requires `@EnableScheduling` on `UserServiceApplication`, already added.

## `airline-core-service` redesign — read before editing this service

`services/airline-core-service` was rebuilt (2026-09-18) against `airline-gds-complete-user-airline-design.md` section 10, adding the onboarding pipeline and membership model the doc requires. Same incremental, breaking-changes-accepted style as `user-service`:

- **`Airline.ownerId`/`updatedById` were removed entirely** — the doc explicitly forbids storing `userId` directly on `Airline` (section 10.5's design note). Airlines are no longer self-serve-created; they only come into existence via onboarding approval (below). There is no `POST /api/airlines` anymore (`405`).
- **New `AirlineMembership` entity/table** (`airline_memberships`, migration `V2`) is the replacement — `userId`/`roleId` are logical cross-service references to `user-service`'s `User`/`Role` (not physical FKs, same convention as everywhere else cross-service data is referenced in this repo), `UNIQUE(user_id, airline_id)`, status `INVITED`/`ACTIVE`/`SUSPENDED`/`REMOVED`. A user can belong to many airlines now — this is a real behavior change from the old one-owner-per-airline model.
- **New onboarding pipeline**: `AirlineOnboardingApplication` (`DRAFT`→`SUBMITTED`→`APPROVED`/`REJECTED`, with `REQUESTED_CHANGES` looping back to `DRAFT`) + append-only `OnboardingReview` history (migrations `V3`/`V4`). Applicant-side API under `/api/onboarding/applications` (`OnboardingController`), admin review API under `/api/admin/onboarding/applications` (`OnboardingReviewController`) — the admin side is restricted to `GDS_ADMIN` at `api-gateway`, not in this service.
- **Approval is one transaction**: creates the `Airline` row from the application's fields, creates an `AirlineMembership` (`status=ACTIVE`, `roleId` = the config value `airline.owner-role-id` — see below) for `initialAdminUserId`, marks the application `APPROVED`, inserts the `OnboardingReview` row. `initialAdminUserId` must be set before approval (`400` otherwise) — per the doc's "Important Rule," the applicant is *not* automatically made the owner; `initialAdminUserId` is explicitly selected/confirmed during review. REJECTED/REQUESTED_CHANGES never throw (a review decision is a normal `200`) — the `noRollbackFor` lesson from `user-service` doesn't apply here.
- **`airline.owner-role-id`** (`application.yaml`/`application-local.yaml`, local value `3`) is a config value, not a runtime Feign lookup to `user-service` — must be kept in sync with the actual `OWNER` role id in `user-service`'s live `roles` table (currently `3`) or approval will silently grant the wrong role. A deliberate simplification (design doc section 18: "cache stable role metadata"), not an oversight.
- **`OnboardingApplicationRequest` now has Bean Validation**: the 4 DB-mandatory fields are required at draft creation (`OnCreate` validation group) but not on update, since the DTO doubles as a PATCH body; `requireCompleteForSubmission` stays as a submission-time safety net against a later PATCH blanking one of them out.
- **`ReviewDecision` moved to `common-lib`** so `OnboardingReviewRequest.decision` could become a real enum instead of a manually `valueOf`-parsed `String`. `GlobalExceptionHandler` (common-lib, repo-wide) gained a generic handler so an illegal enum value in any request body still returns the app's normal error shape instead of falling through to Spring Boot's default.
- **`Airline` field changes**: added `legalName` (kept `name` as the existing display name — not renamed, to avoid rippling through `AirlineDropdownItem` etc.), added `registrationNumber` (nullable, not yet enforced at the DB level), `iataCode`/`icaoCode` are now nullable (doc: "can be optional during early onboarding"). `country` deliberately stays free text, not `country_code` — flagged as a known divergence from the doc, out of scope for this pass. `AirlineStatus` gained `SUSPENDED` (`/suspend` now sets it correctly instead of the old `INACTIVE` misuse).
- **Flyway added** (`services/airline-core-service/src/main/resources/db/migration/`, `V1`–`V5`) — same three-dependency gotcha as `user-service` (`flyway-core` + `flyway-mysql` + `org.springframework.boot:spring-boot-flyway`, or migrations silently never run). `V5` covers the pre-existing, untouched `Aircraft` entity's table too — `ddl-auto` is now `validate`, so every entity needs a matching migration, not just the new ones.
- **`GET /api/airlines/mine`** (was `GET /api/airlines/admin` / `getAirlineByOwner`) now returns a **list** of all airlines the caller has an *active* membership in, not a single owned airline. `PUT`/`DELETE /api/airlines/{id}` now require an active membership of any role (not granular permission-checking yet) instead of an owner match; `PUT` moved from a bodyless-id `PUT /api/airlines` to `PUT /api/airlines/{id}` since a caller can now have more than one airline.
- **Airline lifecycle**: deleting an airline is a **soft delete** (`INACTIVE`) — a hard delete can't work because memberships/aircraft reference it. Members can only edit/close an `ACTIVE` airline; platform-side status changes are `/activate`, `/suspend`, `/ban` (admin-only at the gateway). Airline mutations and onboarding approval evict the Redis caches (`airlines`, `airlinesByUser`, `airlinesDropdown`) — a new mutation path that skips this leaves stale data for the 2h TTL. Known, deferred: `GET /api/airlines/{id}` returns every status plus `registrationNumber` to any signed-in user. Details in the design doc, section 10.1.
- **Breaking change, not yet fixed**: `ancillary-service`, `booking-service`, `flight-ops-service`, and `seat-service` all have a Feign `AirlineClient.getAirlineByOwner()` hitting the now-gone `GET /api/airlines/admin` and expecting a single `AirlineResponse` — that endpoint is `GET /api/airlines/mine` returning a list now. `booking-service`'s client has no fallback configured, so a deserialization error will propagate un-mitigated if it's called. Same accepted-breaking-change posture as `user-service`'s `UserDTO` break to `booking-service`/`payment-service` — deferred, not forgotten.
- **`Aircraft`/`AircraftController`/`AircraftServiceImpl` were left structurally untouched** (pre-existing, out of scope) except that `AircraftServiceImpl` had to be repointed from the removed `AirlineRepository.findByOwnerId` to a membership-based lookup (`getAirlineForUser`, picks the caller's first active membership) so it would still compile — not a redesign of that service.
- **Explicitly deferred, not started**: `OnboardingDocument` + real object storage (R2/S3), `AirlineInvitation`, Feign-based cross-service validation of `userId`/`roleId` against `user-service`, and per-airline role/permission checks (only membership *existence* is enforced; platform-level restrictions live at the gateway).

## `api-gateway` — read before adding routes or endpoints

`cloud/api-gateway` (Spring Cloud Gateway on WebFlux) was rewritten to be the repo's single enforced access-control point:

- **Authentication**: Spring Security validates the bearer JWT (HS256, shared secret, issuer checked). There is no OAuth2 authorization server involved — the "resource server" wiring is just Spring's standard bearer-token validation. `user-service` issues the tokens.
- **Authorization** lives in one default-deny rule table in `SecurityConfig`: public auth routes, platform-admin (`ROLE_GDS_ADMIN`) routes, any-signed-in-user routes, and everything else denied. **A new endpoint is unreachable until it's routed *and* listed there.** Checks are role-based only for now; the rules are written so individual ones can become permission-based later.
- **Not the gateway's job**: airline-scoped decisions ("may this user edit airline N?") — a role in a token can't say which airline, so those stay live membership checks in `airline-core-service`.
- **Identity headers**: the gateway always strips client-supplied `X-User-*` and sets them from the verified token, which is what makes downstream services' trust in those headers safe.
- **Routes** are declared in `application.yaml` (not Java); circuit-breaker settings come from the Config Server, rate limits (Redis) from `RateLimitConfig`. Actuator is on an internal port only.
- **Tests exist** (`mvn -pl cloud/api-gateway test`): an access-matrix test over the whole policy, plus a boot test that catches wiring mistakes. Extend the matrix when adding a route.
